## 1. Overview & goal
Тестовое задание / демо: продающий лендинг из 2 экранов с формой заявки.
После отправки заявки: (1) письмо-уведомление уходит на superhumansmm@yandex.ru
по шаблону из ТЗ, (2) пользователь перенаправляется в Telegram-бота, который
благодарит за регистрацию. Всё должно запускаться локально одной командой и быть
готово к показу проверяющему.

## 4. User scenarios
1. Пользователь открывает лендинг → экран 1 (оффер + CTA), скролл/кнопка → экран 2 с формой.
2. Вводит имя и телефон, жмёт «Отправить» → валидация проходит → показывается «Спасибо, заявка принята!» → через ~2 с редирект в Telegram-бота → жмёт Start → бот: «Спасибо, <имя>! Заявка принята, мы свяжемся с вами».
3. Владелец получает на superhumansmm@yandex.ru письмо: «Новая заявка с сайта <URL>», «Автор: <ФИО>», имя, телефон, время.
4. Пользователь вводит мусор/пустой телефон → inline-ошибка, письмо НЕ уходит, редиректа нет.
5. (Демо для проверяющего) Lily запускает `python app.py` + `python bot.py` → всё работает локально; письмо при тестировании уходит на её тестовый ящик (переключатель TEST_TO_EMAIL).

## 5. Functional requirements
- **FR-1 (лендинг):** 2 экрана в одном HTML (секции), тёмная тема, адаптивно (desktop + mobile ≥360 px), весь текст ≥ 12 px (заголовки крупнее). Экран 1: заголовок-оффер, подзаголовок, CTA-кнопка «Оставить заявку» → плавный скролл к экрану 2. Экран 2: форма и контакты.
- **FR-2 (форма):** поля «Имя» (обязательно, текст) и «Телефон» (обязательно, маска/валидация: 10–15 цифр, допускает +, -, пробелы, скобки). Кнопка «Отправить». Значения полей берутся как есть (безопасный экранинг при выводе).
- **FR-3 (отправка):** POST /api/lead {name, phone, comment?}. Сервер: валидирует повторно, формирует письмо по шаблону FR-5, отправляет SMTP. Успех → JSON {ok: true}; ошибка валидации → 400 {ok: false, error}.
- **FR-4 (редирект):** при ok:true клиент показывает экран «Спасибо» и через ~2 с делает location = https://t.me/<BOT_USERNAME>?start=<urlencoded name>. Если бот не настроен (пустой username в конфиге) — редирект пропускается, остаётся экран «Спасибо».
- **FR-5 (письмо, текст ровно по ТЗ):**
  ```
  Новая заявка с сайта <SITE_URL>

  Автор: <AUTHOR_FIO>

  Имя: <name>
  Телефон: <phone>
  Время: <DD.MM.YYYY HH:MM (Europe/Moscow)>
  ```
  Отправляется на TO_EMAIL (superhumansmm@yandex.ru), тема «Новая заявка с сайта <SITE_URL>». Тема письма и поля — конфиг-переменные, не хардкод.
- **FR-6 (бот):** long-polling скрипт. На /start: если есть payload — «Спасибо, <имя>! Ваша заявка принята, мы скоро свяжемся с вами.»; без payload — общее «Спасибо за регистрацию! ...». На любое другое сообщение — вежливый ответ-заглушка. Одна благодарность за сессию не требуется повторно.
- **FR-7 (конфиг):** config.json (или .env) рядом с кодом: SITE_URL, AUTHOR_FIO, SMTP_HOST/PORT/USER/APP_PASSWORD, TO_EMAIL, TEST_TO_EMAIL (если задан — письма уходят туда, а не клиенту), BOT_TOKEN, BOT_USERNAME. Толерантное чтение: неизвестные ключи игнорируются, отсутствующие → default или явная ошибка с подсказкой при старте.

## 6. Non-functional requirements
- Локальный запуск на Windows 10: `pip install -r requirements.txt` (Flask, python-dotenv или stdlib json; бот — на `requests`/urllib, без python-telegram-bot, если хватит raw API), `python app.py` (лендинг :5000), `python bot.py`.
- Письмо уходит за ≤ 5 с после POST при живом SMTP; при недоступности SMTP — 502 {ok:false}, клиент видит «не получилось, попробуйте позже», редиректа нет (никаких потерянных заявок молча).
- Зависимостей минимум; работает через VPN/толстый линк Lily.
- Код без секретов в git: config.example.json в репо, реальный config.json в .gitignore.

## 7. Architecture
```
[Браузер] --GET /--> Flask app.py --serves--> index.html (2 экрана, JS)
[Браузер] --POST /api/lead--> app.py --SMTP--> superhumansmm@yandex.ru
[Браузер] --redirect t.me/bot?start=имя--> Telegram --> bot.py (polling) --> "Спасибо, имя!"
```
- app.py НЕ хранит заявки (non-goal), только валидирует и шлёт письмо.
- bot.py самостоятелен, общается только с Telegram API; знать о сайте не обязан (имя приходит в payload /start).

## 8. Contracts
- POST /api/lead: body JSON {name: str 1..100, phone: str 10..15 digits после очистки}. Ответы: 200 {ok:true}; 400 {ok:false, error: "invalid_name"|"invalid_phone"}; 502 {ok:false, error:"smtp"}.
- config.json (пример в репо как config.example.json):
  ```json
  {
    "SITE_URL": "http://127.0.0.1:5000",
    "AUTHOR_FIO": "Гринина Лилия",
    "TO_EMAIL": "superhumansmm@yandex.ru",
    "TEST_TO_EMAIL": "",
    "SMTP_HOST": "smtp.yandex.ru",
    "SMTP_PORT": 465,
    "SMTP_USER": "your_login@yandex.ru",
    "SMTP_APP_PASSWORD": "",
    "BOT_TOKEN": "",
    "BOT_USERNAME": ""
  }
  ```
- Тема письма: `Новая заявка с сайта <SITE_URL>`.

## 10. Acceptance criteria
Автоматизированные (pytest, офлайн, без реальной отправки):
- AC-1: POST /api/lead с валидными данными и подменённым SMTP-отправителем (mock) → письмо содержит строки «Новая заявка с сайта …», «Автор: …», «Имя: …», «Телефон: …» и тему с URL; TO_EMAIL = получатель.
- AC-2: POST с пустым именем / телефоном «abc» → 400, письмо не отправлено.
- AC-3: bot-handler на /start с payload «Иван» → текст ответа содержит «Иван»; без payload → содержит «Спасибо за регистрацию».
- AC-4: GET / возвращает HTML с двумя секциями-экранами и формой (name/phone присутствуют).
Ручные:
- AC-5: в браузере: экран 1 → CTA → экран 2 → форма → отправка → «Спасибо» → редирект в бота (если BOT_USERNAME задан) → Start → персональная благодарность.
- AC-6: письмо реально доходит на ящик (при тестах — на TEST_TO_EMAIL) с текстом по FR-5.
- AC-7: невалидный телефон показывает ошибку рядом с полем, письма нет.
